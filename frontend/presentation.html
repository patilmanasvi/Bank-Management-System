Problem Statement & Project Objectives

Addressing architectural bottlenecks in traditional student banking systems

Challenges in Traditional Systems

  • High UI-Database Coupling: Direct SQL queries in UI classes create security and maintenance vulnerabilities.
  • Concurrency Flaws: Without transaction boundaries, simultaneous transfers create race conditions and dirty reads.
  • Unnormalized Schemas: Redundant branch and customer data leads to update and deletion anomalies.

Our Core Objectives

  • Decoupled 3-Tier Layering: Strict separation of Presentation, Java Services, and MySQL Database.
  • Guaranteed ACID Transactions: All-or-nothing atomic fund transfers with automated rollback.
  • Strict 3NF Normalization: 12 relational tables with zero transitive dependencies.
  • Role-Based Access Control: Fine-grained permission model for Customer, Staff, and Admin.

3-Tier System Architecture

Decoupled request/response pipeline from user browser to disk storage

1. Presentation Layer (Web Portal & Desktop GUI)

Vanilla HTML5, CSS3, ES6 JavaScript Web Portal and Java Swing GUI. Communicates with backend via asynchronous HTTP REST JSON requests (fetch API).

2. Application & Business Layer (Java Backend)

Embedded Java HTTP Server (Port 8080) routing to TransactionService, LoanService, and AccountService. Domain OOP models enforce financial rules and concurrency monitors.

3. Database Layer (MySQL 8.0 InnoDB Engine)

12 Normalized 3NF tables. Enforces foreign key constraints, CHECK (balance >= 0) rules, row-level locks, and ACID transaction commits.

Object-Oriented Programming (OOP) Deep Dive

Real-world implementation of the four OOP pillars in Java

Encapsulation

All sensitive financial state (balance, accountNumber) is protected/private. Direct edits are blocked; mutations require synchronized methods with BigDecimal precision.

Inheritance

Person base class extended by Customer and Employee.
Account base class extended by SavingsAccount, CurrentAccount, and FixedDepositAccount.

Polymorphism

Method overriding on withdraw(): SavingsAccount enforces minimum balance, CurrentAccount allows overdraft, and FixedDepositAccount blocks early withdrawal.

Abstraction

Abstract class Account prevents generic instantiation (new Account() is prohibited) while forcing concrete subclasses to implement interest and withdrawal policies.

Database Design & 3NF Normalization

12 Relational Tables in Third Normal Form in MySQL

12 Normalized Tables

  • branch: Locations & IFSC codes
  • customer: KYC, PAN & contact data
  • employee: Staff designations & salary
  • account & account_type: Master accounts & rates
  • transaction: Immutable debit/credit audit trail
  • loan & loan_type: Applications & interest rates
  • login: Role-based credentials

3NF Integrity Guarantees

  • 1NF: All columns store atomic values without repeating groups.
  • 2NF: No partial dependencies on composite keys.
  • 3NF: Eliminated transitive dependencies (branch details isolated in branch table).
  • Constraints: CHECK (balance >= 0) and CHECK (status IN ('ACTIVE','FROZEN','CLOSED')).

ACID Transactions & Concurrency Control

Ensuring atomic financial consistency during inter-account transfers

Transaction Execution Flow (TransactionService.java)

conn.setAutoCommit(false) ➔ Row Lock (SELECT ... FOR UPDATE) ➔ Debit Sender ➔ Credit Receiver ➔ Audit Log ➔ conn.commit()

On Error: conn.rollback() returns database to original state with zero partial balances.

Atomicity

Both debit and credit succeed together, or both rollback completely.

Consistency

System invariants and non-negative balance checks are preserved.

Isolation

InnoDB row locks prevent lost updates during concurrent operations.

Durability

Committed records are written to MySQL Redo Log (WAL) on disk.
