System Goals

Problem Statement & Project Objectives

Addressing architectural bottlenecks in traditional banking software

Challenges in Traditional Software

  • High UI-Database Coupling: Direct SQL in UI files leads to fragile code and SQL injection risks.
  • Concurrency Flaws: Without transaction locks, simultaneous transfers cause dirty reads and lost updates.
  • Unnormalized Schemas: Redundant branch and customer attributes create update/deletion anomalies.

Our Core Project Objectives

  • Decoupled 3-Tier Layering: Clean separation of Browser UI, Java REST Server, and MySQL 8.0.
  • Guaranteed ACID Transactions: All-or-nothing transfers with automated rollback on failure.
  • Strict 3NF Normalization: 12 relational tables with zero transitive dependencies.
  • Role-Based Access Control: Fine-grained permissions for Customers, Staff, and Administrators.
Architecture

3-Tier System Architecture & Data Flow

End-to-end decoupled request/response pipeline

1. Presentation Layer (Web & Desktop GUI)

Vanilla HTML5/CSS3/ES6 JavaScript Web Portal and Java Swing GUI. Communicates via asynchronous REST JSON calls (fetch API).

2. Application Layer (Java Backend)

12 Relational Tables in 3NF. Enforces Foreign Keys, CHECK (balance >= 0) constraints, and ACID transaction locks.

MySQL Schema

Database Design & 3NF Schema Normalization

12 Relational Tables in Third Normal Form in MySQL InnoDB

12 Normalized Tables & Integrity Checks

  • Schema: branch, customer, employee, account_type, account, transaction, beneficiary, card, loan_type, loan, loan_payment, login.
  • 1NF: All columns store atomic values without repeating groups.
  • 2NF: No partial functional dependencies on composite keys.
  • 3NF: Branch IFSC/location isolated in branch table. Zero transitive dependencies.
  • DB Constraints: CHECK (balance >= 0) and CHECK (status IN ('ACTIVE','FROZEN','CLOSED')).

Transactions

ACID Transactions & Concurrency Control

Ensuring atomic financial consistency during inter-account transfers

Transaction Pipeline (TransactionService.java)

conn.setAutoCommit(false) -> Row Lock -> Debit Sender -> Credit Receiver -> Audit Log -> conn.commit()

On Error: conn.rollback() returns database to exact original state.

Atomicity

Both debit and credit succeed together, or both rollback.

Consistency

Balance non-negative invariants are strictly preserved.

Isolation

InnoDB row locks prevent lost updates during transfers.

Durability

Committed records written to MySQL Redo Log (WAL) on disk.

Audit Trail

Audit Logging & Transaction History

Immutable financial ledger auditing with server-side query filters

Financial Compliance & Search Filters

  • Immutable Audit Ledger: Every financial movement (Deposit, Withdraw, Transfer) is logged with immutable timestamps and balance_after tracking. Records can never be overwritten.
  • Server-Side Date Filters: Filter transactions between specific start and end dates (From Date / To Date). Backend safely binds dates in parameterized SQL queries.
  • Transaction Type Filtering: Instant classification by Credit (+) or Debit (-). Color-coded status badges allow rapid visual verification of cash movements.
